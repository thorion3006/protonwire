# Milestone 1 Dependency Spike — 2026-08

Scope (PRD 16.2): select the YAML, nftables, and netlink-route crates; pin
indicative versions; confirm the Proton registry and ProTUN resolution;
record every deviation from the PRD's indicative crate list.

## Decisions

### YAML → `serde_norway` 0.9 (adopted in M1)

- `serde_yaml` is archived and barred by the PRD. `serde_yml` is
  deprecated in turn (its own docs say unmaintained). `serde-saphyr` is
  pre-1.0/alpha. `serde_norway` is the maintained hard-fork of
  `serde_yaml` with a drop-in API and regular releases (0.9.x current).
- Validated in-tree: `protonwire-store`'s loader enforces the 1 MiB input
  cap, and the unit tests prove duplicate-key rejection and
  unknown-field rejection (`crates/store/src/yaml.rs`).
- Residual risk (tracked for T-36, Milestone 2): explicit depth and
  alias-expansion limits are not yet enforced beyond the input-size cap;
  fuzzing of config/profile/group documents lands with T-36. The parser is
  isolated behind `protonwire-store::yaml` so a swap is single-file.

### nftables → `rustables` (recommended; adopted in Milestone 5)

Pure-Rust netlink batches give the transactional atomic-replace semantics
the kill switch requires, with no `libnftnl`/`libmnl` C dependency — which
also keeps packaging simpler. Actively used in the wild (e.g. Synacktiv's
nftables tooling). Fallback if M5 integration fails: mullvad `nftnl-rs`
(battle-tested, needs the C libs). Not added to the lockfile yet: no M1
code calls it, and the stdlib-first policy forbids shipping dependencies
without callers. M5 adoption starts with a compile/link smoke test against
a batch transaction in a network namespace (IT-4).

### Netlink route → `rtnetlink` + `netlink-packet-route` (recommended; adopted in Milestone 5)

Standard stack; the rust-netlink org's activity has slowed, so M5 adoption
begins by checking release health; if stale, fall back to
`netlink-packet-route` over `netlink-sys` with a small hand-written request
loop (our surface is narrow: add/del routes, rules, addresses, marks).
Same no-caller-no-dependency rule as above.

### Q1 — Challenge shapes

- Login is a three-variant flow, not a challenge-then-submit pair:
  `muon::auth::LoginFlow<C>` = `Ok(Session, LoginFlowData)` |
  `TwoFactor(LoginTwoFactorFlow, LoginFlowData)` | `Failed { session,
  reason: FlowErr }` (`src/auth/login.rs:30`). The branch is chosen by
  granted scopes: `loggedin` completes, `twofactor` continues, anything
  else fails (`login.rs:148-170`; scope constants in `src/auth/types.rs:341`).
  `LoginFlowData` = `{ user_id, session_id (the auth UID), password_mode }`.
- The 2FA challenge descriptor is `muon_rest::auth::v4::tfa::TFA`: a
  closed 2-bit `enabled` field (bit 0 TOTP, bit 1 FIDO2) plus an optional
  `FIDO2: fido2::Response` carrying the WebAuthn
  `PublicKeyCredentialRequestOptions` (challenge bytes, rpId,
  allowCredentials, userVerification, extensions) and the registered-key
  list. `LoginTwoFactorFlow` exposes `has_totp()` and
  `fido_details() -> Option<&fido2::Response>` (`login.rs:220-228`).
- Submission is `POST /auth/v4/2fa` with a two-variant body:
  `{"TwoFactorCode": <totp>}` or `{"FIDO2": fido2::Request}` where
  `fido2::Request` = `{ authentication_options, client_data,
  authenticator_data, signature, credential_id }` (base64 assertion
  fields; `muon-rest/src/auth/v4/tfa.rs:57-66`, `fido2.rs:73-91`). A
  successful submission widens scopes and returns the session
  (`login.rs:239-266`); there is no second-round challenge.
- **Contradiction with FR-7L's wording:** there is NO recovery-code
  variant anywhere in pinned muon/muon-rest (`tfa::Post` has exactly
  `TOTP` and `FIDO`). Recovery-code submission therefore fails closed
  with the stable `unsupported-challenge` code in M2; sending a
  ProtonWire-owned `TwoFactorBackupCode` body through `Session::send`
  is the documented future continuation (PRD 6.5 allows owned models
  over the muon transport) but requires a verified continuation
  contract first, per FR-7L's own fail-closed rule.
- Human verification remains blocked-upstream: muon's own roadmap lists
  it unimplemented (README "Roadmap") and the actionable event slot is
  commented out (`src/common/notification.rs:73`). SSO and guest login
  have no surface at all. These keep the stable `blocked-upstream`
  refusals already encoded in `ApiError`.

### Q2 — Store trait (FR-7JB preload)

- `muon::store::Store` (`src/store.rs:29`): `type Key: SessionKeyable`;
  `set_auth(&mut self, key, Auth)`, `remove_auth(&mut self, &Key)`,
  `get_all_auth(&self) -> HashMap<Key, Auth>`, with default
  `set_all_auth`/`remove_all_auth`. Deliberately **synchronous and
  infallible**; writes are fire-and-forget, and the doc block states the
  preload contract verbatim: loading happens **once, at client
  construction** (`AuthStorage::new` calls `get_all_auth()`,
  `src/store.rs:131-137`), is expected to block, and slow backends "should
  pre-load it asynchronously BEFORE feeding it to your Muon client".
  FR-7JB is therefore satisfied by completing the durable read (and
  decrypt) before `Client::builder(..).with_persistence(store).build()`;
  writes go through the bounded facade + serialized worker, which is
  exactly muon's own `examples/fallible-store.rs` pattern (channel to a
  worker, errors surfaced to an observer — the FR-7J persistence-health
  hook).
- Two more behaviors matter: muon refuses two session keys with the same
  UID (`DuplicateUidError`, `src/store.rs:149-166`), and after internal
  token refresh it pushes state to the store and offers
  `Client::sync_stores()` for manual resynchronization
  (`src/common/auth.rs:43-44`, `src/sessions/session.rs` doc). The
  versioned ProtonWire envelope (FR-7C) wraps the serialized
  `SessionCredentials` (PascalCase `UID/UserID/AccessToken/RefreshToken/
  Scopes`, `muon-rest/src/auth/v4/mod.rs:88`); `Auth`/`Tokens` themselves
  serialize too, but token `Debug`/`Display` are redacted upstream
  (`src/auth/types.rs:215-228`) while `user_id`/`uid` are not.

### Q3 — Transport fakeability and the seam decision

**The transport connector cannot be faked from downstream.** The
connector traits (`ConnectTransport`, `ProtonConnectTransport`) live in a
private module re-exported `pub(crate)` (`src/common/mod.rs:1-2`), the
sender trait `InternalSendRequest` likewise (`common/mod.rs:23`), and the
builder's `BuildTransport` is documented as sealed, "cannot be
implemented outside of this crate" (`src/client/builder.rs:63-71`). The
pinned `unsealed` feature lifts sealing only for `Env`, the TLS
upgrader, and the reqwest builder — not the connector. So the S0 fallback
clause applies, and the seam decision is:

1. **State-machine seam (primary): the ProtonWire traits themselves.**
   `AuthenticationApi` and `CatalogApi` in `protonwire-api` are the seam
   core and the S4/S6/S9 fakes implement them (the repo's standard
   `&dyn` injection idiom; the traits stay synchronous and object-safe —
   the S4 adapter bridges to the engine runtime internally, keeping the
   daemon's sync trust boundary intact per the M1 posture above).
2. **Wire seam (adapter-internal tests): the environment/byte layer.**
   A custom `Environment::new_custom(impl Env)` — available because the
   pin already enables `unsealed` (`src/env/mod.rs:117-121`) — whose
   `servers()` returns a loopback `http://` `Server` (`Server` parses
   from a URL and `Scheme::Http` skips TLS entirely,
   `src/common/net.rs:213-229`, `hyper/connector.rs:234-245`), driven
   against a hand-written HTTP/1.1 responder on a std `TcpListener`. This
   exercises the real hyper transport, real SRP proof generation, the
   401-refresh-resend loop, cookie capture, and the direct→indirect
   fallback with full fidelity; muon's own suite takes the equivalent
   approach via its `muon-test-server` dev-dependency.
3. **Recorded limit:** DoH-based indirect-name resolution cannot be
   loopback-faked — the hyper builder always seeds the builtin Google/
   Quad9 DoH services (`hyper/builder.rs:63`, `.doh()` only extends) —
   so the alternative-routing *fallback order* is tested with
   direct-class servers (same `find_available_sender` partition path,
   `src/client/mod.rs:1061-1069`) and full DoH resolution rides only the
   real-muon canary arm (S1/S4).
   `muon-test-server` exists in the Proton registry but is not in the
   committed lockfile (muon dev-dependency); adopting it would be a new
   dependency (stdlib-first policy, spike entry + license review) and is
   unnecessary — the std responder needs no new deps.

### Q4 — ETag support

No first-class ETag machinery exists in muon or muon-rest (grep over
both sources: zero hits). It is not needed: `HttpReq::header` attaches
arbitrary headers (`("If-None-Match", etag)`), `HttpRes::headers()`
exposes the full `http::HeaderMap` (response `ETag` readable,
`src/transport/http/res.rs:106`), and `HttpRes::ok()` accepts 3xx, so a
304 flows back to the adapter (`res.rs:92-100`) where
`is(http::StatusCode::NOT_MODIFIED)` decides `NotModified`. FR-13E's
conditional refresh is implemented entirely at the adapter layer;
`CatalogApi::fetch(etag)` encodes it. `Retry-After` is consumed inside
muon's retry handler (`delay = max(policy, retry_after)`,
`src/common/retry.rs:48`) and also readable from response headers when a
429/503 escapes after retries are exhausted.

### Q5 — Fork selectors

- Parent side: `Session::fork(child_id)` → `ForkFlow` with
  `.payload(bytes)`, `.code(user_code)`, `.independent()`, `.send()` →
  `ForkFlowResult::Success(session, selector)` |
  `Failure { session, reason }` (`POST /auth/v4/sessions/forks`,
  `src/auth/mod.rs:286-356`). The child identifier is conventionally the
  app name; `pvpnclient` does exactly `session.fork(app_name).send()` for
  LocalAgent (`pvpnclient/src/pvpnclient/util/muon.rs:29`).
- Child/import side: `session.auth().from_fork().with_selector(sel)` →
  `WithSelectorFlow::Ok(session, payload) | Failed { .. }`
  (`GET /auth/v4/sessions/forks/{selector}`, sent with
  `no_unauth_session`), or `.with_code()` → poll flow (`GET
  /auth/v4/sessions/forks` returns selector+user code; polling until the
  response stops being 422) (`src/auth/from_fork.rs`). The selector is a
  single-use session-bearing secret — and muon logs it at `info`
  (see Q9).
- M2 uses the parent side to mint the child fork selector for ProTUN
  LocalAgent (PRD 6.5, FR-7C: never share serialized account tokens with
  ProTUN's `ApiSession` cache); `import_fork(selector)` covers FR-7L's
  external-session import. Both are on the S0 trait.

### Q6 — Alternative-routing entry

There is no builder switch. The entry is the environment's server list:
`Env::servers()` for Prod returns `[direct {product}-api.proton.me,
indirect d<base32>.protonpro.xyz]` — the second entry compiled in only
under the pinned `alternative-routing` feature (`src/env/prod.rs:71-77`).
`Client` partitions by `Server::is_direct` and tries all direct servers
before indirect ones (`src/client/mod.rs:1061-1069`), resolving indirect
names via DoH (`src/alternative_routing.rs`, `hyper/connector.rs:170-173`)
and pinning TLS per class (`Env::api_pins` vs `Env::ar_pins`). The adapter
"enables" AR by using the Prod environment with the feature on (already
the pin) — every request, catalog reads included, then falls back
automatically (FR-13A). Fake-coverage limit as in Q3.

### Q7 — Location endpoint

Not modeled. Muon/muon-rest contain no `/vpn` endpoints at all — the
modeled surface is `/auth/v4*`, `/core/v4/users|keys|addresses`, and
`/tests` only. T-31's user-location capture is therefore a
ProtonWire-owned typed model sent through `Session::send_with_sdk`, the
path PRD 6.5 explicitly sanctions for endpoints muon does not model
(single transport, no second Proton HTTP stack). S10 owns the
single-flight/provenance policy; the endpoint never polls
(never-fabricate rule per FR-13B applies to its cached fields too).

### Q8 — Entitlement data

Not modeled. The user model is `core/v4/users` = `{id, name, email,
keys}` — no plan, subscription, or VPN entitlement fields; no scopes
beyond the auth-flow scope strings exist in the surface. S8's entitlement
model (plan tier, NetShield/Secure Core/port-forwarding rights,
gateway/dedicated-server identity) is likewise ProtonWire-owned data over
the muon transport; the FR-7 "detect paid-only feature support" logic
consumes it. `LoginStep::Session` deliberately carries only
`user_id`/`session_id` so no entitlement shape is frozen before S8.

### Q9 — The FR-7P TOTP-at-info log claim

**Confirmed verbatim, and it is not alone.** The TOTP emission:
`src/auth/login.rs:271` builds `format!("sending TOTP request with code:

### Adapter-facing facts recorded for S2/S4 (no question, load-bearing)

- **Retry:** default `RetryPolicy` retries 429/5xx 3× with backoff and
  ≤3 s jitter, honoring `Retry-After` (`src/common/policy.rs:111-122`,
  `retry.rs:44-60`). `RetryPolicy::never()` and per-request
  `.retry_policy()` exist, so ER-17's fail-closed paths pin `never()` on
  their requests and the adapter sets a deliberate default at build.
- **Refresh:** on 401 muon refreshes once (`POST /auth/v4/refresh`,
  grant_type refresh_token) and resends; refresh failure →
  `AuthErr::Refresh`, session-gone → `AuthErr::Session` with local auth
  removal (`src/common/auth.rs:96-141`). `Session::refresh_auth()`
  forces it; `Session::logout()` is infallible by design (remote DELETE
  best-effort, local state always cleared, `src/sessions/session.rs:258`).
- **Events:** `with_notification_receiver` yields `RateLimited` /
`InternalServerError` informational events (capacity 100, must be
drained) — the upstream signal feeding S2's `RateLimited` event variant.
- **Unauth sessions:** the first send on a credential-less session
  mints and *persists* an anonymous API session unless the request sets
  `no_unauth_session` (`src/common/auth.rs:57-81`). The adapter must
  expect `Auth::Anonymous` store entries and not treat them as logins.
- **Cookies:** muon captures/strips/reinjects the `Session-Id` cookie
  through the injectable `CookieStore` trait (`src/cookie_store.rs:21`);
  `without_cookie_store()` opts out. Persisting that cookie rides the
  S4/S5 store decision (pvpnclient feeds it to LocalAgent alongside the
  fork selector).
- **Construction:** the hyper builder requires an injected
  `OperatingSystem` (resolver/TCP/time via the public `muon::rt`
  traits) plus an executor (`examples/shared/mod.rs`); `App::new`
  takes `"<platform>-<product>@<semver>"` and the pinned `other-product`
  feature admits our VPN product string, which selects the
  `vpn-api.proton.me` host in Prod.

## M2 S6 — catalog wire seam, fixture provenance, dependency records (2026-08-19)

Answers deferred by S0's seam decision, recorded for S4/S7.

### Live recording of `/vpn/logicals` is blocked without fingerprinting

Probing the real endpoint (2026-08-19): both `api.protonvpn.ch` and
`vpn-api.proton.me` return `422 Code 5003` ("app no longer supported")
for unversioned clients; with a current `x-pm-appversion` the response
becomes `401 Invalid access token`; and anonymous session minting
(`POST /auth/v4/sessions` with an empty body) returns
`422 Code 8004 Operation not allowed` — Muon only attaches the
device-fingerprint body when an info provider supplies one
(`src/common/auth.rs:377`). Recording the live catalog would mean
forging anti-abuse fingerprints against production, which is out of
bounds. The committed fixture
(`crates/store/src/catalog_fixture.json`) is therefore grounded
field-for-field in the deserialization models of Proton's maintained
clients — win-app master (`LogicalServerResponse`,
`PhysicalServerResponse`, `ServersResponse`, `BaseResponseDetail`),
android-app master (`LogicalServer`, `ConnectingDomain`,
`LogicalsResponse`), and python-proton-vpn-api-core stable
(`LogicalServer`, `PhysicalServer`) — which together cover every field
generation the API ships (legacy `Location{Lat,Long}`, current
`EntryLocation`/`ExitLocation`, per-protocol entries, `GatewayName`,
`StatusReference`, `Translations`). Values are synthetic; names, types,
nullability, and presence are the recorded contract, enforced with
`deny_unknown_fields` so upstream drift fails loudly. The same fixture
file serves the adapter's wire tests (`crates/api/src/catalog.rs`
includes it across crates), making transport and model provably share
one contract.

### Adapter-facing facts for S4 (no question, load-bearing)

- **`TimeCapabilities` cannot be constructed without one `unsafe impl
  Monotonic`**: the trait is an empty marker with no safe
  implementation anywhere in muon or proton-os-interface (every
  downstream — muon's own test util, proton-vpn-rcrl,
  proton-vpn-local-agent — writes this exact impl), and no upstream
  type implements both `InstantFactory` and `SystemTimeFactory`. The S6
  test seam carries the one scoped `#[allow(unsafe_code)]` in
  `protonwire-api` with the justification comment; the workspace
  `unsafe_code = deny` rule keeps holding everywhere else.
- **The sync bridge must drive a multi-thread runtime.** Blocking a
  *current-thread* tokio runtime via `Handle::block_on` from a foreign
  (non-runtime) thread deadlocks in the connector: the kernel completes
  the TCP handshake (a std listener accepts it) but tokio's connect
  future never wakes, because nothing pumps the IO driver. A
  `new_multi_thread` runtime blocks correctly from the caller's
  thread. S4's engine-runtime bridge must not use current-thread
  runtimes for the sync-to-async crossing.
- **`no_unauth_session` is `pub(crate)`**: a credential-less session
  mints an anonymous API session before its first real request
  (`POST /auth/v4/sessions`; `Scopes` parses from a JSON array; the
  response is PascalCase `UID/UserID/AccessToken/RefreshToken/Scopes`
  and `UserID: null` is fine). Any loopback fake must script that
  exchange; the minted `Bearer` token then authorizes the catalog GET,
  which the S6 responder asserts.
- **Catalog request shape that passes muon's audit**:
  `HttpReq::new(GET, "/vpn/logicals").allowed_time(30s).service_type(
  ServiceType::Background, true)` — "Background: examples: cache
  refresh" in muon's own taxonomy; the GET is idempotent so transports
  may be raced. Conditional refresh is one `header(("If-None-Match",
  etag))`; 304 passes `HttpRes::ok()` (3xx-tolerant) and
  `res.is(Status::NOT_MODIFIED)` classifies it, per Q4.
- **Responder discipline**: `Connection: close` per exchange interacts
  cleanly with hyper's pooling (one TCP connection per request, no
  keep-alive bookkeeping in the fake); read/accept timeouts on the
  responder turn protocol stalls into test failures instead of hangs.

### S4 canary-arm finding (2026-08-19): two transport-layer disclosure sites, Q9 table extended

The real-muon canary arm (m2-plan S1's attached S4 gate) found two
leak sites the Q9 source-reading pass missed — the arm exists precisely
to catch what source reading misses. Both are muon 2.6.1 transport
layer:

1. **`muon::transport::http::req` logs the whole request at WARN** —
   the fork selector RIDES THE PATH
   (`is using the default time constraint self=GET /auth/v4/sessions/forks/{selector}`),
   so the selector class reaches the writer at EVERY allowed runtime
   level (error..trace).
2. **`muon::transport::http::hyper::sender` (plus its http1 sibling at
   trace) logs full request objects INCLUDING BODIES at DEBUG** —
   `sending request with hyper req=Request { .., body: Some(b"{...}") }`
   — so every credential traveling a body leaks at debug/trace:
   username (`/auth/v4/info`), TOTP (`/auth/v4/2fa`), FIDO assertions,
   refresh tokens, the fingerprint payload.

Neither site is coverable by value scrubbing (peer-derived values must
never enter the registry), so before-formatting suppression is the only
control. **Remediation (validated against the full real-muon arm —
login, TOTP, store, fingerprint, session-keys, from_fork selector —
passing `assert_no_secrets_reach_logs` at all five levels, 2.7 s run):
`("muon::transport", Level::ERROR)` added to `MODULE_CAPS` in
`crates/core/src/redact.rs`.** Request objects carry paths and bodies,
and paths and bodies carry secrets at every level below ERROR; the
subtree's diagnostics are the price of closing the class. The stub arm
and the policy table pins extend in the same commit so CI holds the
class without real muon.

**Sec review round 1 extension (same class, two more P1 sites + one
P2):** the S4 security review source-verified two further uncapped
disclosure sites and one cap-insufficient one, proving the transport
cap did not complete the FR-7P table:

1. **`muon::common::retry` (P1 → capped WARN)**: `RetryHandler::send`
   logs `debug!("received {res}")` on EVERY successful response —
   unconditionally; `RetryPolicy::never()` kills only the retry loop —
   and `HttpRes`'s manual Debug prints the entire HeaderMap with
   values. `Set-Cookie` rides it un-stripped (RetryHandler sits below
   CookieSender in the sender stack; the adapter's NoOpCookieStore
   returns Pass). Fix: `("muon::common::retry", Level::WARN)` — its WARN
   sites carry only status/delay strings. A scripted-`Set-Cookie` step
   joins the real-muon arm with the S4 fix round.
2. **`muon::common::auth` (P1 → dropped ENTIRELY)**: the module logs
   the UID at WARN (`session unauthorized`, :103) and ERROR (:121) —
   exactly the levels its S1 WARN cap kept — and the WARN path fires at
   the DEFAULT production level (`RUST_LOG=info`) on the routine
   token-expiry cycle. No `Level` floor can drop ERROR, and FR-121 is
   not deviable, so the filter gained a `MODULE_DROP_ALL` arm
   (coordinator decision: drop-all + adapter-side redacted diagnostics
   where the typed `AuthErr` surfaces, rather than a recorded
   deviation).
3. **`muon::doh` (P2 → capped INFO)**: resolved IP sets at DEBUG/TRACE
   (`debug!(?res, "found")`, `RData {rd:?}`) and full DNS responses at
   trace; FR-121 forbids full IPs. INFO keeps the safe `info!(%err)`.

All three landed with stub-arm shapes + policy pins in
`crates/core/src/redact.rs` (red observed in-tree: the UID reaching the
writer at `RUST_LOG=error` through the module's own error site, and the
cookie through the retry debug site).

**Correction (S4 fix round, captured-output evidence):** item 1's
"Set-Cookie rides un-stripped on every send" premise is FALSE at pinned
muon 2.6.1 — `retry.rs:42` formats the response via **Display**
(`received http::Response { status: 200 OK, error_code: None }` — no
headers); the header-carrying Debug (`res.rs:59-67`) is logged nowhere
upstream. The sec review conflated Display and Debug. The
`("muon::common::retry", WARN)` cap STAYS as an engine-upgrade trap
guard (a future muon logging the Debug — headers, Set-Cookie un-stripped
below CookieSender — is already suppressed; the real-muon arm's
scripted-Set-Cookie step now pins exactly that direction), and items 2
(the UID at WARN/ERROR — empirically live, reproduced red) and 3 (doh
IPs) stand unchanged. The lesson for the record: source-citation reviews
must distinguish `{}` (Display) from `{:?}` (Debug) before declaring a
leak live; empirical capture is the tiebreaker.

## M2 S5c — the keyring dependency mini-spike (2026-08-23)

Decision 7's one open dependency call: `zbus` vs `keyring` vs
`secret-service` for the `keyring` writable session store (FR-7B/FR-7E;
the S5b fail-closed `Deferred` variant was awaiting exactly this
audit). Method: crates.io/docs.rs metadata plus two scratch-crate
resolves and runs on the pinned 1.97.1 devshell (`/tmp`, nothing in the
repo tree), then source reading of the pinned copies under
`CARGO_HOME/registry/src`.

### The three-way comparison (decision 7)

| Option | Verdict | Why |
| --- | --- | --- |
| `zbus` direct (hand-written Secret Service client) | rejected | A D-Bus Secret Service client is NOT a tiny fraction (collections, sessions, DH session encryption, item attributes) — the stdlib-first policy's own bar: don't reinvent wheels this size. |
| `secret-service` direct | rejected | Correct pure-Rust wheel, but lower-level than the envelope store needs (session/algorithm handling we'd re-encapsulate); it is also the transitive the adopted stack already wraps. |
| `keyring` ecosystem | **adopted** | The maintained facade over `keyring-core` + per-platform stores; on Linux the store is `zbus-secret-service-keyring-store` (pure-Rust zbus + RustCrypto crypto) — but adopted at the keyring-core layer, not the facade (see the facade finding). |

### Deviations from the PRD's indicative pins (both recorded here)

1. **`keyring = "3"` (PRD 16.2) → the v4 ecosystem at the keyring-core
   layer.** v3's Secret Service path is `sync-secret-service` →
   `dbus-secret-service` 4.1.0 → **`libdbus-sys`** (C, links the
   system libdbus) — verified by scratch resolve; v3's `linux-native`
   is kernel **keyutils** (volatile, process-session-scoped — not the
   freedesktop Secret Service FR-7B names). v4's zbus store is the
   pure-Rust path; PRD 16.2 itself defers final versions to technical
   design (this spike).
2. **No `keyring` facade (v3 or v4).** The v4 facade's `v1` module
   installs its platform store through a one-time global
   (`SET_CREDENTIAL_STORE_RESULT`, v1.rs) that both bypasses and
   defeats `keyring_core::set_default_store`: a probe program that
   installed the mock store FIRST still wrote a REAL `protonwire`
   secret to the live service (verified and deleted), and on a bus-less
   runner the facade hard-fails every `Entry::new` with `NoDefaultStore`
   because `zbus Store::new()` connects eagerly. Testability and CI
   (no Secret Service on runners) both demand the explicit-store
   `keyring-core` API; the facade's own docs bless linking keyring-core
   directly for exactly this. The feature pin
   (`zbus-secret-service-keyring-store = { features = ["crypto-rust"] }`)
   mirrors keyring 4.1.6's own declaration verbatim.

### The dev-environment question (mock backend)

The v4 facade has **no** `mock` feature; `keyring-core` 1.0 ships the
mock store unconditionally (`keyring_core::mock::Store`) — so the tests
inject it per-test through `KeyringSessionStore::with_store(Arc<dyn
CredentialStore>)`: no process-global default-store mutation, no
shared entry, and **no D-Bus daemon is needed or contacted anywhere in
the suite**. The live zbus arm's busless refusal is pinned
environment-gated the CONTRIBUTING rule-5 way: it asserts the typed
`Bind`/`Unavailable` refusal on runners without
`DBUS_SESSION_BUS_ADDRESS` (stock CI) and NOTICE-skips on bus-bearing
developer boxes.

### Decision: ACCEPT, and what landed

`ResolvedWritableStore::Keyring(KeyringSessionStore)` is real (S5b's
`Deferred` refusal for `keyring` is retired; `tpm2` keeps it — decision
2). Behavioral red first: `explicit_keyring_resolves...` observed red
against the S5b `resolve` (panicked on `Deferred { store: Keyring }`)
before any implementation. Landed shape, `crates/store/src/writable_store.rs`:

- **Entry semantics**: one entry (`service "protonwire"`, `user
  "session"`) — the single-account daemon's one session, the same
  identity the file store gives `/var/lib/protonwire/session.json`;
  the strict parse (unknown fields, schema, digest) and the
  generation-monotonicity refusal apply to service bytes exactly as to
  file bytes.
- **FR-7JA by construction**: binding to the live service is LAZY —
  `resolve` answering `keyring` constructs nothing and connects
  nothing; availability is INJECTED (`SecretServiceStatus`) because
  the answer is deployment-owned. The daemon's wiring passes
  `Unavailable` until the S5c agent-registration protocol ships the
  brokered store (the one process the live arm is legal in is the
  credential agent, the account owner); `auto` prefers the keyring when
  `Available` (FR-7B order) and records the typed
  `SecretServiceUnavailable` skip otherwise; explicit `keyring` under
  `Unavailable` refuses fail-closed (new
  `WritableStoreError::SecretServiceUnavailable`, same no-fallback
  rule as `Deferred`). A failed bind is retried on the next operation —
  a restarted session bus must not poison the process.
- **PeerSecret transit**: `get_secret` bytes move into `Zeroizing`
  transit on arrival; values leave the module only across
  `SecretBoundary::ingress` (`load_credentials`), exactly once (pinned).
- **Typed, byte-free error mapping**: upstream keyring errors reduce to
  `SecretServiceFailure` (`Unavailable`/`Undecodable`/`Ambiguous(n)`/
  `Rejected(detail)`/`Other`) + the operation (`Bind`/`Load`/`Save`);
  `BadEncoding`/`BadDataFormat` (which carry raw secret bytes upstream)
  are discarded to their kind — verified by test, including that the
  refusal's Display carries no secret bytes.

Residuals (accepted, recorded): the Secret Service protocol decrypts
the secret inside zbus buffers this crate cannot zeroize (inherent to
the dependency; the file store's transit is fully zeroized); the size
cap on load is post-allocation (the service allocates before this
crate can size-check; the file store gates at fstat first — the
service's own item limits bound the exposure); the daemon-side brokered
store is the S5c agent-protocol unit's, not this one's.
